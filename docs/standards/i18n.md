# Internationalization

All application UI text lives in one typed catalog owned by the app; shared helpers are copied, not depended on.

## Rules

- **Default:** the small-dictionary approach below. Advanced pluralization, translator or TMS workflows, or richer formatting justify an established localization library as an exception.
- Dictionaries, glossary, supported languages, and the language control stay in the app.
- All application UI text lives in one catalog tree. Never add dictionaries beside components (`*-copy.ts`, `Record<Locale, …>` objects, `locale === 'nl' ? … : …` branches): they escape the `satisfies` check and the parity test, and split one area's text across two homes. Extend the module that already owns an area; nest a subtree rather than reconcile wording.
- Messages are data: strings or nested objects of strings, never functions. Use `fmt` for placeholders and `plural` for count forms. Callers pass derived values (rounding, page counts, casing, optional parts) in; a variant that drops a placeholder gets its own key. Non-text types, such as tab or filter unions, live with their feature.
- Backend functions and plain data modules never hold a display string. Name each entry by a key from the union the schema defines and resolve it in the catalog, typed so a missing entry fails compilation.
- Validators return a key (`'enterName'`), not a sentence; the form resolves it at render.
- Never read a message inside an effect: hold a key in state and resolve it at render. An effect whose dependencies exclude the locale pins stale text; adding the locale to them is usually the wrong fix.
- Translate accessible names, placeholders, titles, toasts, empty and error states, and canvas labels. Keep user-authored content distinct from application UI copy.
- Pure domain modules accept needed messages as arguments and never import React hooks.
- Locale-specific formatting (decimal separators, date locale tags) lives in small runtime helpers, so screens never branch on the locale.
- The language control labels each available language explicitly; no hardcoded two-language toggle when more locales are supported. A new locale needs a complete dictionary and a language-control label.

## Implementation

1. Copy the [core helpers](i18n/examples/core.ts) and only the adapters the target needs: [web provider](i18n/examples/index.tsx), [TanStack SSR](i18n/examples/server.ts), [optional Clerk sync](i18n/examples/clerk-sync.tsx) (`@clerk/react`, Core 3), or [native provider](i18n/examples/native.tsx). Copy them together into an app-owned runtime directory, preserving relative imports. An app with a tested implementation keeps it and compares example fixes deliberately.
2. Start with inline dictionaries; when they grow, split them into area modules in the catalog directory and compose them into the root tree. Do not freeze a dictionary with `as const` if its literal values are the target-language type:

   ```ts
   type MealName = 'breakfast' | 'lunch'; // the schema's union
   const en = {
     actions: { save: 'Save' },
     logged: 'Added {food} to {meal}',
     results: { one: '1 result', other: '{count} results' },
     meals: { breakfast: 'Breakfast', lunch: 'Lunch' } satisfies Record<MealName, string>,
   };
   const nl = { /* … */ } satisfies typeof en;
   const locales = ['en', 'nl'] as const;
   ```

3. Call `createI18n` once at module scope. It binds the module-level provider, hooks, and helpers to the app's types; pass its `config` to the provider (and the optional `LanguageSync`). Read messages at render:

   ```tsx
   export const { config: i18nConfig, LocaleProvider, useI18n, readClientLocale } = createI18n({
     locales, fallback: 'en', messages: { en, nl },
   });
   <LocaleProvider config={i18nConfig} initialLocale={locale}>{children}</LocaleProvider>;
   const { messages: copy } = useI18n();
   fmt(copy.logged, { food, meal });
   plural(locale, count, copy.results);
   ```

   Define components and hooks at module scope, never inside a factory: Biome 2.6's recommended `noComponentHookFactories` rejects nested ones. To migrate a factory-based copy rather than suppress the rule, recopy the examples, pass `config` to each `LocaleProvider`, and replace `createLanguageSync(…)` with `<LanguageSync config={config} />`.

4. Web: for SSR, resolve the request's explicit language cookie, then Accept-Language, then the fallback, using the server adapter. Pass that locale to the initial provider and html `lang` to avoid a hydration mismatch; browser navigation uses the client resolver. Keep server adapter imports out of client-only modules. Put the provider around app content, preserving the framework's document and scripts placement. Optional Clerk metadata sync must not override an explicit local choice; inspect the copied adapter's contract.
5. Native: import only the native and core examples, supply device locales and storage adapters, and start with a synchronously available locale. Keep DOM, SSR, and Clerk-web imports out of native bundles.
6. Move any dictionary outside the catalog into the area module that owns it, convert functions to placeholders and plural forms, delete the source file, and point component test mocks at the real dictionary. Fix inline locale branches the same way.

## Verify

- Copy [message-parity test support](i18n/examples/test-utils.ts) into test-only code, never production code, and call `assertMessageParity({ en, nl })` from a Vitest test. It checks key sets, empty values, and placeholder parity, so it only protects text inside the catalog.
- Run types and tests after every extraction.
- Verify layouts, long translations, language persistence, startup hydration, user switching, SSR refresh, and supported native targets.
