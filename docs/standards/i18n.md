# Internationalization

Dictionaries, glossary, supported languages, and UI controls stay in the app; shared helpers are copied, not depended on.

## Rules

Small dictionaries can remain inline initially; when they grow, split them into area modules in the catalog directory and compose them into the root tree:

```ts
const en = { actions: { save: 'Save' }, welcome: 'Hello {name}' };
const nl = { actions: { save: 'Opslaan' }, welcome: 'Hallo {name}' } satisfies typeof en;
const locales = ['en', 'nl'] as const;
const messages = { en, nl };
```

Do not freeze the dictionary with `as const` if using literal values as the target-language type. Initialize the copied createI18n factory once:

```tsx
const { LocaleProvider, useI18n, readClientLocale } = createI18n({
  locales, fallback: 'en', messages,
});
// In a component:
const { messages: copy } = useI18n();
return <button>{copy.actions.save}</button>;
```

**Required — one catalog.** All application UI text lives in that tree. Do not add dictionaries beside components (`*-copy.ts`, `Record<Locale, …>` objects, `locale === 'nl' ? … : …` branches): they escape the `satisfies` check and the parity test, and they split one area's text across two homes. Before adding an area, extend the module that already owns it; nest a subtree rather than reconcile wording.

**Required — messages are data.** Values are strings or nested objects of strings, never functions:

```ts
const en = {
  logged: 'Added {food} to {meal}',
  results: { one: '1 result', other: '{count} results' },
};
fmt(copy.logged, { food, meal });
plural(locale, count, copy.results);
```

Callers compute derived values (rounding, page counts, casing, optional parts) and pass them in; use a separate key when a variant drops a placeholder. Types that are not text, such as tab or filter unions, live with their feature.

**Required — text stays out of backend and plain data files.** A backend function or a plain data module never holds a display string. Name each entry by a key from the union the schema defines and resolve it in the catalog, typed so a missing entry fails compilation:

```ts
type MealName = 'breakfast' | 'lunch';
const en = { meals: { breakfast: 'Breakfast', lunch: 'Lunch' } satisfies Record<MealName, string> };
```

Adding a union member then fails the types until both locales name it.

**Required — validators return a key.** A validator reports `'enterName'`, not a sentence; the form resolves the key at render.

**Required — no message reads in effects.** Hold a key in state and resolve it at render. Reading a message inside an effect whose dependencies should not include the locale pins stale text; adding the locale to the dependencies is usually the wrong fix.

Use fmt for placeholders and plural for count forms. Add translated accessible names, placeholders, titles, toasts, empty/error states, and canvas labels. Keep user-authored content distinct from application UI copy. Pure domain modules accept needed messages as arguments; they must not import React hooks.

## Implementation

Keep dictionaries, glossary, supported languages, and UI controls in the app. Use the [core helpers](i18n/examples/core.ts) and only the adapters needed by the target: [web provider](i18n/examples/index.tsx), [TanStack SSR](i18n/examples/server.ts), [optional Clerk sync](i18n/examples/clerk-sync.tsx), or [native provider](i18n/examples/native.tsx). Copy selected files together into an app-owned runtime directory, preserving their relative imports. No @appelent/i18n dependency is required.

### Web and native

For SSR resolve the request's explicit language cookie, Accept-Language, then fallback using the server adapter. Pass that same locale to the initial provider and html lang to avoid hydration mismatch. On browser navigation use the client resolver without an unnecessary server round trip. Keep server adapter imports out of client-only modules. Put the provider around app content; preserve the framework's document/scripts placement.

The language control is app-owned. Use explicit labels for each available language rather than a hardcoded two-language toggle when more locales are supported. Optional Clerk metadata sync must not override an explicit local choice; inspect the copied adapter's contract.

Native code imports only the native/core examples, supplies device locales and storage adapters, and starts with a synchronously available locale. Verify persistence, startup hydration, and user switching. Keep DOM/SSR/Clerk-web imports out of native bundles.

## Verify

Copy [message-parity test support](i18n/examples/test-utils.ts) into test-only code and call it from a Vitest test:

```ts
assertMessageParity({ en, nl });
```

It checks key sets, empty values, and placeholder parity, so it only protects text inside the catalog. Do not import it into production code. Where the project has a structure check, make it reject new dictionaries outside the catalog directory and locale comparisons whose branches are text; keep locale-specific formatting (decimal separators, date locale tags) in small runtime helpers so screens never branch on the locale. Run types and tests after every extraction, then verify layouts, long translations, language persistence, SSR refresh, and supported native targets. A new locale requires a complete dictionary and language-control label.

## Migration

For dictionaries outside the catalog, move each into the area module that owns it, convert functions to placeholders and plural forms, delete the source file, and point component test mocks at the real dictionary. Fix inline locale branches the same way.

Inventory @appelent/i18n and subpath imports, copy the needed runtime adapters, redirect imports locally, and keep the app's existing dictionary shape and cookie/storage names. Port its parity tests before removing the package. Existing apps can keep their tested implementation; compare fixes in these examples deliberately rather than overwriting it during toolkit sync.

For advanced pluralization, translator/TMS workflows, or richer formatting requirements, evaluate an established localization library. This small dictionary approach is an explicit app choice, not a requirement for every project.
